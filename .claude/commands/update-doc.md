# Update Documentation Command

이 명령어는 KubeDB Monitor 프로젝트의 문서 시스템(.agent/)을 초기화하고 업데이트하는 데 사용됩니다.

## 사용법

```bash
/update-doc initialize           # 문서 시스템 초기화
/update-doc [주제]               # 특정 주제에 대한 문서 업데이트
/update-doc sop [SOP 이름]       # 새로운 SOP 생성 또는 업데이트
```

## 명령어 실행 시 수행 작업

### 1. initialize 모드

**목적**: 프로젝트를 처음 분석하여 .agent/ 문서 시스템을 초기화하거나 전체 재생성

**수행 단계**:

1. **프로젝트 스캔**:
   - 디렉토리 구조 분석
   - 주요 파일 및 컴포넌트 식별
   - 기술 스택 파악
   - 의존성 확인

2. **System 문서 생성/업데이트**:
   - `.agent/system/architecture-overview.md`: 시스템 아키텍처 재작성
   - `.agent/system/project-structure.md`: 최신 프로젝트 구조 반영
   - `.agent/system/event-pipeline.md`: 이벤트 처리 파이프라인 업데이트

3. **SOPs 검증**:
   - 기존 SOP 파일 목록 확인
   - 누락된 필수 SOP 식별 및 생성 제안

4. **Task 아카이브 정리**:
   - `task/` 디렉토리 내 파일 정리
   - 완료된 작업을 `task/completed/`로 이동 제안

5. **중앙 인덱스 업데이트**:
   - `.agent/readme.md`: 모든 문서 링크 및 가이드 최신화
   - 문서 메트릭 업데이트

6. **CLAUDE.md 동기화**:
   - 프로젝트 루트의 `CLAUDE.md`와 `.agent/readme.md` 내용 일관성 확인
   - 필요 시 동기화

### 2. 일반 업데이트 모드

**목적**: 특정 주제나 컴포넌트에 대한 문서 업데이트

**수행 단계**:

1. **변경 사항 분석**:
   - Git 변경 이력 확인
   - 수정된 파일 목록 파악
   - 영향받는 컴포넌트 식별

2. **관련 문서 식별**:
   - 업데이트가 필요한 문서 파일 찾기
   - `.agent/readme.md`에서 관련 섹션 확인

3. **문서 업데이트**:
   - 변경 사항을 반영하여 문서 수정
   - 새로운 기능은 적절한 위치에 추가
   - 폐기된 내용 제거

4. **링크 및 참조 업데이트**:
   - 깨진 링크 수정
   - 새로운 문서 간 상호 참조 추가

5. **검증**:
   - 모든 문서가 Markdown 형식에 맞는지 확인
   - 링크가 올바르게 작동하는지 검증

### 3. SOP 생성 모드

**목적**: 새로운 표준 운영 절차 문서 생성 또는 기존 SOP 업데이트

**수행 단계**:

1. **SOP 범위 정의**:
   - 사용자가 요청한 프로세스 이해
   - 관련 컴포넌트 및 파일 파악
   - 선행 조건 및 후행 조건 식별

2. **SOP 구조 설계**:
   - 목적 및 적용 대상
   - 단계별 워크플로우
   - 체크리스트
   - 자주 발생하는 문제 및 해결 방법
   - 관련 문서 링크

3. **SOP 파일 생성**:
   - `.agent/SOPs/[sop-name].md` 파일 생성
   - 템플릿 기반으로 내용 작성
   - 실제 프로젝트 구조와 명령어를 반영한 구체적인 예시 포함

4. **중앙 인덱스 업데이트**:
   - `.agent/readme.md`에 새 SOP 추가
   - "상황별 문서 찾기" 섹션에 사용 사례 추가

5. **CLAUDE.md 업데이트**:
   - 필요 시 메모리 파일에 새 SOP 규칙 추가

## 문서 작성 규칙

### A. 파일 네이밍

- **System 문서**: `kebab-case.md` (예: `architecture-overview.md`)
- **SOPs**: `kebab-case.md` (예: `agent-modification-workflow.md`)
- **Task**: `YYYY-MM-DD-feature-name.md` (예: `2025-10-08-session-recording.md`)

### B. 문서 구조

모든 문서는 다음 구조를 따라야 합니다:

```markdown
# 문서 제목

## 목적 (또는 개요)
[이 문서의 목적을 1-2문장으로 명확히 기술]

## 주요 내용
[섹션별로 구성]

## 관련 문서
[다른 문서로의 링크]

## 버전 히스토리 (선택 사항)
- **v1.0** (YYYY-MM-DD): 초기 작성
```

### C. 링크 규칙

- **상대 경로 사용**: `[문서명](../system/architecture-overview.md)`
- **명확한 링크 텍스트**: "여기를 클릭" 대신 "아키텍처 개요 문서" 사용
- **깨진 링크 금지**: 링크 작성 후 반드시 파일 존재 여부 확인

### D. 코드 예시 규칙

- **실제 프로젝트 파일 경로 사용**: 가상의 경로 금지
- **실행 가능한 명령어**: 모든 bash 명령어는 실제 실행 가능해야 함
- **주석 포함**: 복잡한 명령어는 설명 주석 추가

### E. 스타일 가이드

- **한글 사용**: 모든 문서는 한글로 작성 (코드 및 명령어 제외)
- **명확한 표현**: 애매한 표현 대신 명확하고 구체적인 표현 사용
- **일관된 용어**: 동일한 개념은 항상 동일한 용어 사용
  - ✅ "Agent" (일관됨)
  - ❌ "Agent", "에이전트", "Java Agent" (혼재)

## 문서 업데이트 시 필수 확인 사항

### 체크리스트

- [ ] 변경된 내용이 `.agent/readme.md`에 반영되었는가?
- [ ] 새로운 문서는 적절한 디렉토리에 위치하는가?
- [ ] 모든 문서 간 상호 참조 링크가 올바른가?
- [ ] `CLAUDE.md`와 `.agent/readme.md`의 규칙이 일관되는가?
- [ ] 코드 예시가 최신 프로젝트 구조를 반영하는가?
- [ ] 폐기된 정보는 제거되었는가?
- [ ] 새로운 SOP는 실제로 실행 가능한 단계로 구성되었는가?

## 자주 묻는 질문

### Q1: 언제 update-doc을 실행해야 하나요?

**A**: 다음 상황에서 실행하세요:
1. 주요 기능 구현 완료 후
2. 아키텍처 변경 후
3. 새로운 컴포넌트 추가 후
4. 에이전트의 반복적인 실수를 수정한 후 (SOP 생성)
5. 프로젝트 구조 변경 후

### Q2: initialize와 일반 업데이트의 차이는?

**A**:
- **initialize**: 전체 문서 시스템을 처음부터 재구성 (프로젝트 시작 시 또는 대규모 리팩토링 후)
- **일반 업데이트**: 특정 변경 사항만 기존 문서에 반영 (일상적인 기능 개발 후)

### Q3: SOP는 언제 생성하나요?

**A**: 다음과 같은 경우 SOP를 생성하세요:
1. 에이전트가 동일한 실수를 반복할 때
2. 복잡한 프로세스를 여러 번 수행해야 할 때
3. 새로운 팀원 온보딩 시 참고할 절차가 필요할 때
4. 중요한 배포 절차를 표준화해야 할 때

## 에이전트에게 전달되는 지침

**이 섹션은 AI 에이전트가 읽는 내부 지침입니다.**

### 초기화 시 (initialize)

1. **프로젝트 분석**:
   - `find . -type f -name "*.java" -o -name "*.go" -o -name "*.tsx" -o -name "*.yaml"` 실행하여 주요 파일 목록 파악
   - `ls -la` 로 루트 디렉토리 구조 확인
   - `cat README.md` 로 프로젝트 개요 파악
   - `cat CLAUDE.md` 로 기존 규칙 파악

2. **문서 생성 우선순위**:
   1. `.agent/system/architecture-overview.md`
   2. `.agent/system/project-structure.md`
   3. `.agent/system/event-pipeline.md` (이벤트 기반 시스템인 경우)
   4. `.agent/readme.md` (마지막에 생성, 모든 문서 링크 포함)

3. **내용 작성 시 주의사항**:
   - 실제 파일 경로 사용 (추측 금지)
   - 실제 디렉토리 구조 반영
   - 코드베이스에 존재하는 실제 클래스명, 함수명 사용

### 일반 업데이트 시

1. **변경 분석**:
   - `git status` 로 변경된 파일 확인
   - `git diff` 로 변경 내용 파악
   - 변경 영향 범위 분석

2. **문서 매핑**:
   - Agent 코드 변경 → `system/architecture-overview.md`, 관련 SOP
   - Control Plane 변경 → `system/architecture-overview.md`
   - Dashboard 변경 → `system/architecture-overview.md`
   - 이벤트 스키마 변경 → `system/event-pipeline.md`, `docs/agent-event-data-structures.md`
   - 배포 방식 변경 → `SOPs/deployment-workflow.md`

3. **업데이트 방법**:
   - 기존 내용 읽기 → 변경 사항 반영 → 검증
   - 폐기된 정보는 삭제하고 새 정보로 대체
   - 버전 히스토리에 변경 이력 추가

### SOP 생성 시

1. **사용자 의도 파악**:
   - 어떤 프로세스를 표준화하려는가?
   - 이 SOP는 누가 언제 사용하는가?
   - 선행 조건은 무엇인가?

2. **SOP 구조**:
   ```markdown
   # [SOP 제목]

   ## 목적
   ## 적용 대상
   ## 워크플로우 단계
   ## 체크리스트
   ## 자주 발생하는 문제 및 해결 방법
   ## 관련 문서
   ## 버전 히스토리
   ```

3. **실행 가능성 보장**:
   - 모든 명령어는 실제 실행 가능해야 함
   - 파일 경로는 프로젝트에 실제 존재해야 함
   - 단계별로 검증 방법 포함

### 금지 사항

- ❌ 가상의 파일 경로 사용 금지
- ❌ 실행 불가능한 명령어 작성 금지
- ❌ 추측으로 문서 작성 금지 (불확실하면 사용자에게 질문)
- ❌ 기존 CLAUDE.md의 규칙과 충돌하는 내용 작성 금지

### 필수 사항

- ✅ 모든 문서는 한글로 작성
- ✅ `.agent/readme.md`는 항상 최신 상태 유지
- ✅ 새 문서 생성 시 반드시 `.agent/readme.md`에 링크 추가
- ✅ `CLAUDE.md`와 `.agent/readme.md`의 일관성 유지
- ✅ 실제 프로젝트 구조 및 코드 반영
